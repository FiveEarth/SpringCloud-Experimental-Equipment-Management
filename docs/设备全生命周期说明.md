# 实验工具管理平台 · 设备全生命周期说明

本文档描述从设备录入到报废的完整业务流程，以及前后端对应关系，便于验收与排查问题。

---

## 一、全生命周期流程概览

```
实验室管理 → 设备录入(含实例) → 预约(可选) → 领用 → 使用中 → 归还 → [维护/维修] → 报废
     ↑              ↑              ↑         ↑        ↑         ↑           ↑          ↑
   lab_lab      lab_equipment   lab_equipment_reserve  lab_equipment_apply   lab_equipment_maintain  lab_equipment_scrap
               lab_equipment_asset
```

---

## 二、分阶段流程（按角色）

### 1. 基础数据（管理员）

| 步骤 | 操作 | 前端入口 | 后端接口 | 说明 |
|------|------|----------|----------|------|
| 1.1 | 实验室管理 | 实验室管理 → 新增/删除 | `GET /api/lab/lab/list`<br>`POST /api/lab/lab/batchAdd`<br>`POST /api/lab/lab/batchDelete` | 需 ADMIN/TEACHER，请求头带 `X-Roles` |
| 1.2 | 设备录入 | 设备管理 → 新增设备 | `GET /api/device/devices`<br>`POST /api/device/equipment/batchAdd` | 新增时按「数量」自动生成 `lab_equipment_asset` 实例 |
| 1.3 | 设备编辑 | 设备管理 → 编辑 | `PUT /api/device/equipment/{id}` | 可改编号、名称、型号、实验室、采购日期、规格、说明书、数量、状态 |
| 1.4 | 设备状态/删除 | 设备管理 → 在库/故障/报废、批量删除 | `PUT /api/device/equipment/{id}/status`<br>`POST /api/device/equipment/batchDelete` | 需 ADMIN/TEACHER |

### 2. 预约流程（学生 ↔ 管理员/教师）

| 步骤 | 操作 | 前端入口 | 后端接口 | 说明 |
|------|------|----------|----------|------|
| 2.1 | 学生提交预约 | 我的预约 → 新建预约 | `GET /api/device/devices?borrowable=true`<br>`POST /api/reserve/createReserve` | 选设备、预约日期、开始/结束时段；日期格式 `yyyy-MM-dd`，时间 `yyyy-MM-dd HH:mm:ss` |
| 2.2 | 管理员/教师审批预约 | 预约审批 | `GET /api/reserve/queryAllReserve`<br>`PUT /api/reserve/approve/{id}?status=1|2` | status=1 通过，2 驳回；需带 `X-Roles` |
| 2.3 | 学生查看预约 | 我的预约 | `GET /api/reserve/queryReserveByUserId` | 可修改、撤销、延长、报修、领用 |

### 3. 领用与归还（学生 ↔ 管理员/教师）

| 步骤 | 操作 | 前端入口 | 后端接口 | 说明 |
|------|------|----------|----------|------|
| 3.1 | 学生看到「待领用预约」 | 我的领用 | `GET /api/reserve/queryReserveByUserId`<br>`GET /api/apply/applies/user/{userId}` | 已通过且未领用的预约 + 领用记录合并展示 |
| 3.2 | 学生点击领用（来自预约） | 我的领用 → 预约行「领用」 | `POST /api/apply/apply/startBorrow` body: `{ reserveId }`，Header: `X-User-Id`, `X-User-Name` | 生成领用记录、分配实例、标记预约已领用 |
| 3.3 | 学生直接领用（未预约） | 我的领用 → 提交领用申请 | `POST /api/apply/apply` | 需管理员/教师在「领用审批」通过（若存在该页面）；当前菜单为「归还审批」，直接领用需审批时需有领用审批入口 |
| 3.4 | 领用审批（可选） | - | `GET /api/apply/applies/pending`<br>`POST /api/apply/apply/approve/{id}` | 仅「直接领用申请」需要；预约后领用无需审批 |
| 3.5 | 学生申请归还 | 我的领用 → 领用中 → 申请归还 | `POST /api/apply/apply/return/apply/{id}` Header: `X-User-Id` | 记录进入待归还审批 |
| 3.6 | 管理员/教师确认归还 | 归还审批 | `GET /api/apply/applies/pendingReturn`<br>`POST /api/apply/apply/return/approve/{id}` body: `approved, equipmentStatus, approvalUserName` | 通过后释放实例或加回数量，可选设备正常/故障（故障则实例置维修中） |

### 4. 维护/维修（学生/教师/维修员 ↔ 管理员）

| 步骤 | 操作 | 前端入口 | 后端接口 | 说明 |
|------|------|----------|----------|------|
| 4.1 | 提交报修/维护 | 我的预约 → 报修；或维修相关页 | `POST /api/maintain/maintain` | equipmentId, maintainType(0日常/1维修), applyUserId, maintainContent, progressStatus |
| 4.2 | 维修员接单/完成 | 待维修列表 / 工作台 | `GET /api/maintain/maintains/repairer`<br>`POST /api/maintain/maintain/{id}/accept`<br>`POST /api/maintain/maintain/{id}/complete`<br>`POST /api/maintain/maintain/{id}/reject` | 维修员角色 |

### 5. 报废（管理员/维修员）

| 步骤 | 操作 | 前端入口 | 后端接口 | 说明 |
|------|------|----------|----------|------|
| 5.1 | 提交报废申请 | 报废审批或维修相关 | `POST /api/scrap/scrap` | 需 ADMIN/TEACHER/REPAIR，带 `X-Roles`、可选 `X-User-Id` |
| 5.2 | 审批报废 | 报废审批 | `GET /api/scrap/scraps/pending`<br>`GET /api/scrap/scraps`<br>`POST /api/scrap/scraps/{id}/approve` body: `status, disposalMethod` | 通过后设备类型 status=3（已报废） |

## 四、权限与请求头

以下请求头由前端在**全局 axios 请求拦截器**中统一添加（已登录且存在时）：

- `Authorization: Bearer {token}`
- `X-User-Id`：当前用户 ID
- `X-Roles`：角色列表，逗号分隔，如 `ADMIN`、`TEACHER,STUDENT`
- `X-User-Name`：当前用户姓名

后端据此做权限校验的接口示例：设备批量增删改、实验室增删、预约审批、报废列表与审批、领用审批（若单独存在）等。学生端仅需 `X-User-Id`/`X-User-Name` 用于领用、归还、预约创建。

## 五、数据表与设备粒度

- **lab_equipment**：设备类型（名称、型号、实验室、数量、状态等）；数量与 `lab_equipment_asset` 条数一致。
- **lab_equipment_asset**：设备实例，每条对应一台实物；领用/归还时分配或释放的是实例（asset_id）。
- **lab_equipment_apply**：领用/归还记录；可关联 `reserve_id`、`asset_id`；审批通过时优先分配实例并写入 `asset_id`。
- **lab_equipment_reserve**：预约记录；状态 0 待确认、1 已确认、2 已取消、3 已完成；`is_used` 表示是否已转为领用。
- **lab_equipment_maintain**：维护/维修记录；可关联 `asset_id`。
- **lab_equipment_scrap**：报废记录；按设备类型（equipment_id）维度，通过后设备类型 status 置为 3。

## 六、完整生命周期串联示例

1. **管理员**：实验室管理新增实验室 → 设备管理新增设备（数量 N，自动生成 N 条 asset）。
2. **学生**：我的预约 → 新建预约（选设备、日期、时段）→ 提交。
3. **管理员/教师**：预约审批 → 通过。
4. **学生**：我的领用 → 看到「预约已通过，点击领用」→ 点击「领用」→ 变为「领用中」。
5. **学生**：使用完毕后，我的领用 → 该条「申请归还」。
6. **管理员/教师**：归还审批 → 确认归还（可选设备正常/故障）。
7. （可选）**学生/教师**：报修 → **维修员**：待维修列表接单、完成。
8. （可选）**管理员/维修员**：报废申请 → **管理员/教师**：报废审批通过 → 设备类型状态变为已报废。

以上流程覆盖：**基础数据 → 预约 → 审批预约 → 领用（预约转领用）→ 归还申请 → 批准归还 → 维护/维修 → 报废**，全生命周期可在此闭环内完整实现。

## 七、已知注意点与可选 SQL

- **历史数据**：若库中已有 `lab_equipment` 但无对应 `lab_equipment_asset`，可执行 `docs/db-adapt-gra-optional.sql` 中「补全设备实例」注释块（按需取消注释并执行）。
- **领用审批**：当前菜单仅有「归还审批」；若开放「直接领用申请」且需审批，需在菜单中增加「领用审批」入口，对应 `GET /api/apply/applies/pending` 与 `POST /api/apply/apply/approve/{id}`。
